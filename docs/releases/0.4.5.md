# v0.4.5 — Linux packages for Ubuntu 22.04 and Debian 12, and no more crash on older CPUs

The Linux packages now run on more systems. Through 0.4.4 they were built on Ubuntu 24.04 and needed its C library
(glibc 2.38) and GCC 13's C++ library, so on Ubuntu 22.04, Debian 12 or Linux Mint 21 they stopped before doing
anything ("GLIBCXX_3.4.31 not found"). From 0.4.5 they are built on Ubuntu 22.04 (glibc 2.35, GCC 12) and run there
and on everything newer. The depth maps are the same bytes as 0.4.4's.

The Windows AMD package no longer crashes on a CPU older than its payload. It now says what is missing and, paired
into Meshroom, leaves that node to Meshroom's own binary.

## What changed

The measurements are in docs/04 ("0.4.5: x86-64 ISA tiers measured and dropped" and "0.4.5: Linux bundles for
glibc 2.35").

**Linux bundles from an Ubuntu 22.04 container.** Both Linux packages are built in a jammy container on the build box
(`scripts/linux/jammy`): the same dependency versions (Eigen 3.4.0, Ceres 2.2, OpenImageIO 3.0.17, Boost 1.86),
configured as before, with GCC 12 instead of 13. The newest symbol versions any file needs are now `GLIBC_2.35` and
`GLIBCXX_3.4.30`, checked at build time. On a bare `ubuntu:22.04` container every library of both bundles resolves
and every program starts (`scripts/linux/jammy/loadtest.sh`); 0.4.4's bundle fails the same test.

**A CPU check for the Windows payloads.** The rocm7.2 payloads (RDNA3 and RDNA4 cards) are built for x86-64-v3 (AVX2
and FMA: Intel Haswell 2013, AMD Excavator 2015 / Zen 2017 and newer), the hip6.2 payloads for AVX (Sandy Bridge,
Bulldozer). On an older CPU a node died on its first such instruction. The package now checks the CPU before choosing
a payload; when the CPU lacks a feature, `cheshire-detect.exe` exits 3 naming it, `cheshire-run.cmd` prints the
reason, and the Meshroom launcher runs Meshroom's own binary for the node (unless `CHESHIRE_BACKEND=cheshire` asks
for the package, which then stops and says why).

**Measured and dropped: CPU-specific builds (ISA tiers).** The plan was a second, AVX2 build of the Linux and Windows
CUDA packages, chosen by CPU. An AVX2 build of Eigen sums in a different order and changes the results, and with
Eigen kept at its old width the AVX2 build was no faster: the Linux CUDA bundle took 571 s on the 41 views either
way, with the same depth maps. Results that depend on the user's CPU are not worth a few seconds, so there is one
build per package, as before.

## Validation

Each package was checked as the file you download where its card was available (docs/04, "The 0.4.5 release round").

| package | hardware | 2025.1: mini6 | 2025.1: 41 views | 2023.3: mini6 |
|---|---|---|---|---|
| Windows AMD | RX 9070 (rocm7.2 gfx12-generic payload) | 19/19 | base 297 s, verify 691 s, experimental 272 s, fastransacexp 252 s, verifyexp 702 s | 4/4 |
| Linux AMD | RX 6750 XT (house-pc) | 7/7 | experimental 511 s, and 581 s with 0.4.4's steps off: the same depth maps | 1/1 |
| Linux CUDA | GTX 1080 Ti (house-pc), the same code (below) | 7/7 | experimental 581 s | 1/1 |
| Windows CUDA | not run on an NVIDIA card in this release (below) | | | |

Every run passed, and every depth map is the 0.4.4 gate's on the same card byte for byte, except the RX 9070's two
`cpufallback` runs (CPU SIFT's features differ from run to run). Both Linux tarballs load on a bare Ubuntu 22.04. This release was planned as 0.5.0;
the Windows AMD zip was composed again after its gate to change that number in one comment of `cheshire-run.cmd`, and
its other 1,286 files are the gated zip's byte for byte.

**The Linux CUDA tarball itself was not run on the GTX 1080 Ti**: the card was out of house-pc again when it was built.
A jammy build of the same code passed all nine runs on it with 0.4.4's depth maps, and the release tarball is that
build byte for byte in 325 of 332 files. The other seven, the CUDA libraries, have the same GPU code and the same host
instructions, differing only by the module identifiers nvcc generates per build.

**The Windows CUDA zip was not run on an NVIDIA card in this release**, nor in 0.4.0 to 0.4.4: its test box is still
down. Its eight new-pipeline programs ran this gate's 41-view Photogrammetry Experimental command lines on the RX 9070
box from the zip alone; all finished, and SfMExpanding placed all 41 cameras within 0.0028 % of the scene's radius of
the AMD zip's reconstruction. The Windows AMD zip's hip6.2 payloads (RDNA1, and RDNA2 under Windows) were not run on a
card either; their code is the gated payloads' code, compiled for their targets by the same chain.

## Also

* **Known:** CPU SIFT (`--forceCpuExtraction`, or the fallback when the card has no GPU SIFT code) is upstream's, and
  its features differ from run to run. GPU SIFT repeats exactly.
* **Known:** neither Windows zip can write a USD file, as in 0.4.0.
