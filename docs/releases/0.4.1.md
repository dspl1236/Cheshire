# v0.4.1 — the same output in half the time: an 884-photo job in 5,269 s instead of 10,930, and SfM that repeats itself at that size

The False Door, 884 photos through Photogrammetry Experimental Fast Ransac on Meshroom 2025.1 and an RX 9070, took
10,930 s with 0.4.0 (and this release's RDNA4 matcher kernel dropped in) and takes 5,269 s with 0.4.1: DepthMap 5,587 s
to 1,733 s, Texturing 2,480 s to 1,245 s, the new SfM chain 1,168 s to 699 s. Every change of ours gives the same
output as the code it replaces, byte for byte. The one output on our test sets that differs from 0.4.0's is
Texturing's UV layout, because upstream took one of our bug reports (below). And SfMExpanding now repeats itself on a set this size: run again, the
whole job gives the same cameras and landmarks, byte for byte.

## What changed

The measurements are in docs/04 (the sections "After 0.4.0") and docs/07 (the matcher's last section).

**FeatureMatching on the cards' integer dot-product units.** Two new kernels for the GPU search, chosen per card,
with the same matches as before by construction (integer sums, ties to the lower row) and checked on every query of
eight engine-bay pairs:
- `knn2_wmma` on RDNA4 (`v_wmma_i32_16x16x16_iu8`): FeatureMatching on 41 views 9.9 s to 4.0 s on the RX 9070, the
  engine bay 57.3 s to 25.6 s;
- `knn2_dot4q` on NVIDIA (sm_61 and later) and RDNA2: 41 views 13.1 s to 9.8 s on the GTX 1080 Ti; the search
  kernels 1.9x on the RX 6750 XT.

RDNA1 and RDNA3 keep the 0.4.0 kernel until they are measured; `CHESHIRE_MATCHER_KERNEL=u8|sliced|dot4q|wmma`
picks one.

**The host work in the False Door's logs** (steps 10a-10g), found in a full run of 0.4.0 and each exact:
- **10a**, FeatureMatching's GPU search and geometric filter at the same time;
- **10b**, the regions loaded on every core, each descriptor file in one read;
- **10c**, a binary copy of the tracks file beside the JSON, for the nodes after TracksBuilding;
- **10d**, SfM's residual statistics and outlier filters on every core;
- **10e**, DepthMap's T cameras from each camera's own landmarks, listed once (a chunk's startup 111 s to 12 s);
- **10f**, the images folder listed once, not once per view (about 20 s of every DepthMap and Texturing process);
- **10g**, the image cache's oldest slot by load order: clock()'s millisecond ties evicted read-ahead images before
  their use, so texturing read most images twice.

**DepthMap** (steps 10h, 10j, 10k), now bound by its GPU stages:
- **10h**, a tile's depth list from its camera's own landmarks, not a walk over all 1.31 million for the camera and
  again for each T camera: the False Door's whole DepthMap node 4,257 s to 2,247 s of chunk time;
- **10j**, no wait for the device per tile: the fused SGM pass keeps its column minima in the stream's own buffer and
  the colour optimisation keeps its textures (HIP's buffer free and texture teardown each waited);
- **10k**, a batch's maps written on their own thread and the next batch's images decoded while the device runs, and
  the images' headers and the tiles' T cameras on every core: a False Door chunk 98.4-102.0 s to 83.7-85.2 s.

**SfMExpanding repeats itself on large sets** (step 10i). Each round's next views were ranked by score alone after a
parallel loop, so tied scores at the round's cutoff went in the threads' order and the False Door's reconstruction
varied from run to run; ties now go by view id. Three False Door runs the same bytes.

**AliceVision develop f2447d4.** The submodule moved from 2cb1a39 to f2447d4, which carries two fixes from this
project: [alicevision/AliceVision#2179](https://github.com/alicevision/AliceVision/pull/2179) (the Mesher reads its
neighbour-inversion count as an int), whose own copy here (step 4u) is gone, and
[alicevision/AliceVision#2181](https://github.com/alicevision/AliceVision/pull/2181) (UVAtlas sorts each chart's
camera candidates by their projected areas, which it had truncated to integers before comparing). The second
changes Texturing: the charts keep other cameras and pack differently, so `texturedMesh.obj` and the atlases differ
from 0.4.0's (on mini6, 270,994 UV vertices against 270,476), as upstream intends, and texture digests from 0.4.0 do
not carry over. Every other output on the test sets is the same bytes as before the move. The move also brings
upstream's corrections of the radial4 and fisheye1 Jacobians and of the SO3 logarithm at a half turn, so SfM with
cameras of those models can differ from 0.4.0's.

The Windows packages and the Linux CUDA package were built at e7bee63, the Linux HIP package at 4d7a6ca: the same
sources, with the Linux build scripts' architecture setting restored (below).

**The Linux build setting.** The AliceVision update fixed a bug in its own build: the CPU architecture flags of
`TARGET_ARCHITECTURE` were dropped on every second cmake run, which is how Cheshire's Linux builds have always been
made. Our Linux scripts asked for `core`, so with the fix this round's first Linux build came out as `-march=core2`
code that no gate had run. The scripts now ask for what every Linux release has actually been, `TARGET_ARCHITECTURE=none`
with `USE_SSE2=ON` (the x86-64 baseline with AliceVision's SSE paths), and the Linux HIP package built that way matches
the bundle its card gated in all 353 of its files. The Linux CUDA package is the gated file itself. For users nothing
changes: the Linux packages are built as every earlier one was, and the Windows builds were never affected.

## Validation

Each package was checked as the file you download, on its own card where one was available: the Linux packages are
byte for byte the builds their cards gated (docs/04, "The 0.4.1 release round").

| package | hardware | 2025.1: mini6 | 2025.1: 41 views | 2023.3: mini6 |
|---|---|---|---|---|
| Windows AMD | RX 9070 (rocm7.2 gfx12-generic payload) | 19/19 | base 332 s, verify 721 s, experimental 308 s, fastransacexp 282 s, verifyexp 721 s | 4/4 |
| Linux AMD | RX 6750 XT (house-pc) | 7/7 | experimental 576 s | 1/1 |
| Linux CUDA | GTX 1080 Ti (house-pc) | 7/7 | experimental 636 s (and twice more, below) | 1/1 |
| Windows CUDA | not run on an NVIDIA card in this release (below) | | | |

Every run passed. On the RX 9070 every configuration's depth maps are 0.4.0's gate's on the same card byte for byte,
except `cpufallback`, whose digest has changed with every release since 0.3.6. The 41-view runs take 13-18 % less than
in 0.4.0's gate. On the GTX 1080 Ti, 41 views ran three times: with the self-checks on, with every change since 0.4.0
switched off (and the matcher on its 0.4.0 kernel), and as shipped; the last two are identical node by node, matches
included, except the one file that records its run's folder.

**The Windows CUDA zip was not run on an NVIDIA card in this release**, nor in 0.4.0: its test box is still down. It got
0.4.0's smoke test: its eight new-pipeline programs ran this gate's 41-view Photogrammetry Experimental command lines on
the RX 9070 box from the zip alone, all finished, and SfMExpanding placed all 41 cameras within 0.0028 % of the scene's
radius of the AMD zip's reconstruction. If you run it on a card, a note on how it went is welcome.

The Windows AMD zip's hip6.2 payloads (RDNA1, and RDNA2 under Windows) were not run on a card in this release either:
the box that held those cards is the one that is down. Their code is the gated payloads' code, compiled for their
targets by the same chain.
