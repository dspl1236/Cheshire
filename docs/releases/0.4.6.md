# v0.4.6 — the Linux AMD package on boards without PCIe atomics, GPU SIFT on upstream's PopSIFT, and a CPU path that repeats

The Linux AMD package no longer crashes on machines whose board has no PCIe atomics. 0.4.5's bundle segfaulted in
FeatureExtraction on the first photograph there (exit 139): the HIP runtime on Linux refuses any kernel that may call
the host from the GPU on such a board, PopSIFT v0.10.0's orientation kernel had a debug `printf`, so it never ran, and
the describer was handed features that had never been filled in. 0.4.6 runs on such a machine (an FX-8120 on a PCIe 2.0
board) end to end. Windows was never affected.

GPU SIFT moves from PopSIFT v0.10.0 to upstream's develop branch, on upstream's own HIP port. Upstream's orientation
votes changed, so the features differ slightly from 0.4.5's; the reconstruction is the same within a few hundredths of
a percent.

## What changed

The measurements are in docs/14 ("Upstream's own HIP port") and docs/04 (steps 16a and 16b, and "The 0.4.6 release
round").

**PopSIFT pinned at develop 54f42f3.** Cheshire now builds upstream's HIP port with a small overlay instead of its own
port of v0.10.0. Cheshire's fixes for it are merged upstream (alicevision/popsift#201, #202, #203 and #205). The overlay
keeps the image pyramid in layered textures on HIP, because the HIP runtime on Windows will not allocate a plain 3D
array wider than 2048 (filed as ROCm/rocm-systems#14652 and alicevision/popsift#206). The describer is now compiled
against the headers of the PopSIFT it links; with the new library's settings layout, the old headers would corrupt
memory. On the 41 monstree views (RX 9070): 23,617 features per view against 23,627, 41 of 41 cameras posed both times,
91,475 landmarks against 91,494, residual 1.3147 against 1.3123.

**No kernel may call the host.** `scripts/check_hostcall.py` reads every kernel in a Linux bundle's GPU libraries and
fails the build on any that needs a hostcall buffer (apart from four PopSIFT debug kernels nothing launches). PopSIFT
now returns an empty result, not unfilled memory, when an image has nothing to download, so a failed kernel costs the
image its features instead of the run.

**16a, CPU SIFT in a stable order.** Upstream's CPU SIFT appended each keypoint's descriptors in the order the threads
finished, so the features changed from run to run. Each keypoint now gets a slot of its own, filled in loop order: the
output is upstream's single-threaded output on every run, and a third faster than the threaded loop (41 views, 49-51 s
to 33-34 s). `CHESHIRE_SIFT_SORT=0` keeps the arrival order.

**16b, the CPU matcher's kd-trees from `random_seed` on Windows.** vcpkg's FLANN ignores the seed AliceVision passes and
shuffles each tree from `std::random_device`, so the Windows CPU matcher (and Meshroom's own Windows build) gave
different matches every run. The build now detects that FLANN and builds a seeded copy of its kd-tree index, as
AliceVision's own FLANN fork does on Linux. Filed upstream as alicevision/AliceVision#2210. `CHESHIRE_FLANN_SEED=0`.
With 16a and 16b, the `cpufallback` configuration (CPU SIFT, CPU matcher) gives the same depth maps on every run.

**Bundle adjustment with an undistortion model.** The fused projection cost covered cameras with both a distortion
and an undistortion model, where upstream applies only the distortion. Since alicevision/AliceVision#2202 upstream
combines the two, so the fused cost now steps aside for any camera with an undistortion model. No test camera has
one, and the test sets' cameras are unchanged.

## Validation

Each package was checked as the file you download where its card was available (docs/04, "The 0.4.6 release round").
The features changed with the PopSIFT pin, so the references are the pin's development builds of 2026-10-28, not 0.4.5.

| package | hardware | 2025.1: mini6 | 2025.1: 41 views | 2023.3: mini6 |
|---|---|---|---|---|
| Windows AMD | RX 9070 (rocm7.2 gfx12-generic payload) | 19/19 | base 293 s, verify 701 s, experimental 263 s, fastransacexp 243 s, verifyexp 717 s | 4/4 |
| Linux AMD | RX 6750 XT on lgpu-pc (no PCIe atomics) | base, twice | base 644 s | |
| Linux CUDA | GTX 1080 Ti (house-pc) | 7/7, and base again | base 576 s, experimental 596 s; 0.4.5's bundle, base 576 s | 1/1 |
| Windows CUDA | not run on an NVIDIA card in this release (below) | | | |

Every run passed. On the RX 9070, mini6 `base` gives the pin's development build's depth maps byte for byte, as do the
eight configurations that change only how the work is done, and on the 41 views the features, posed cameras,
landmarks and residual are the same as that build's. The `cpufallback` depth maps are those of 16b's two development
runs. On lgpu-pc, the machine 0.4.5's Linux bundle crashed on, the release tarball's depth maps are those of the pin's
Linux bundle, with the same features, cameras, landmarks and residual.

**On the GTX 1080 Ti** the CUDA PopSIFT at the new pin finds the AMD packages' features exactly: 23,617 per view on
the 41 views and 23,687 on mini6, with the same ranges. mini6 `base` gave the same depth maps twice. Against the
published 0.4.5 CUDA bundle on the same card and the same 41 views: 41 of 41 cameras posed both times, 91,324
landmarks against 91,377, residual 1.3147 against 1.3140, and the same time (576 s).

**The Windows CUDA zip was not run on an NVIDIA card in this release.** Its GPU SIFT is the same PopSIFT source as the
Linux CUDA package's. Its eight new-pipeline programs ran this gate's 41-view Photogrammetry Experimental command
lines on the RX 9070 box from the zip alone. All finished, and SfMExpanding placed all 41 cameras within 0.0010 % of
the scene's radius of the AMD zip's reconstruction. The Windows AMD zip's hip6.2 payloads (RDNA1, and RDNA2 under
Windows) were not run on a card either; their code is the gated payloads' code, compiled for their targets by the
same chain.
