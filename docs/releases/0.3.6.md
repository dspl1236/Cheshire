# v0.3.6 — Meshroom 2025.1

Cheshire now pairs into Meshroom 2025.1.0 as well as 2023.3. The packages needed no change for it:
every paired node's binary takes every option 2025.1 passes it. What changed is around them. The
DepthMap node override has a 2025.1 version, since 2025.1 ships its node descriptions as source. The
pairing scripts handle both layouts. The gate harness works around two `meshroom_batch` behaviours
of 2025.1 that anyone scripting it will meet too (below). GPS-radius pairing, opt-in since 0.3.5, is
fixed for cameras that omit `GPSAltitudeRef`, and was measured on a 524-photo drone survey. The
gate checks more: PrepareDenseScene, a CPU-only fallback run, and nodes the pairing declined.

## What changed

Per-step numbers, boxes and checks are in docs/04.

**Meshroom 2025.1.** The Meshroom layout is the one 2023.3 has: `aliceVision/bin` holds the node
binaries, and the photogrammetry template runs the same twelve nodes. The node descriptions moved
from `lib/meshroom/nodes/aliceVision/*.pyc` to `aliceVision/share/meshroom/aliceVision/*.py`.
- **Pairing:** `meshroom-pair` pairs both versions, and its option check passes all nine nodes
  against 2025.1's own binaries.
- **The DepthMap override:** it gives chunks of 48 views instead of 12 (0.3.4) and now has a 2025.1
  version, `DepthMap.2025.py`. Pairing keeps Meshroom's `DepthMap.py` as `DepthMap.py.meshroom`, a
  name the node loader skips. The override loads it and changes only the block size, so node
  versions and cache keys stay Meshroom's. `--unpair` puts Meshroom's file back.
- **Unpairing** no longer says "restored" over a binary that a running node still holds.

**Two `meshroom_batch` behaviours in 2025.1**, found by the first gate run, which looked empty:

- **`--cache` is ignored, on Windows and Linux.** `executeGraph` saves an unsaved graph to a
  temporary project before computing, and the cache follows it to `<temp>/MeshroomCache`. Use
  `--save <dir>/project.mg` instead: the cache is then `<dir>/MeshroomCache`. `--save` and
  `--cache` together also end up in the temp folder.
- **On Windows `meshroom_batch.exe` re-launches itself.** Its start-up script calls `os.execv`
  unless `ALICEVISION_LIBPATH` already lists the Meshroom folder. On Windows that starts a new
  process and ends the first, so a script waiting on the process sees it exit in half a second while
  the graph computes in the copy. Set `ALICEVISION_LIBPATH` (and `PYTHONPATH`) as that script
  would, or wait for the child. The gate harness does the first, and the second as a fallback.

**2025.1 raised two RANSAC limits, and they cost time.** FeatureMatching's `maxIteration` went
from 2048 to 50000, and StructureFromMotion's `localizerEstimatorMaxIterations` from 4096 to 50000.
Both loops are host AC-RANSAC and run very nearly their whole budget.

| set | geometric filtering | SfM | views placed |
|---|---|---|---|
| 41 photos | 1.5 s to 35 s | 47 s to 135 s | 41 either way |
| engine bay, 107 photos | 21 s to 488 s | 40 s to 75 s | 107 either way |
| False Door, 884 photos | 105 s to 2234 s | | 830 against 815-833 at the old limits |

The larger budget verifies more weak pairs (+13 % and +72 %), but no set placed more views. The
False Door's landmarks were 5 % fewer. To get 2023.3's speed, override
`FeatureMatching:maxIteration=2048` and `StructureFromMotion:localizerEstimatorMaxIterations=4096`.
Moving the hypothesis loop to the device is on the roadmap.

**GPS-radius pairing on a real survey (6w).** OpenDroneMap's "zoo" survey (CC0, 524 photos, GPS in
every EXIF) found a bug first. Upstream's `hasGpsMetadata()` requires all six GPS tags, and the
Sony DSC-WX220 writes no `GPSAltitudeRef`, which EXIF makes optional, so no view was paired by GPS.
The altitude reference is now optional (absent means above sea level). Then:

| image pairing | pairs | verified | views placed | FeatureMatching |
|---|---|---|---|---|
| vocabulary tree (Meshroom's rule above 200 photos) | 13,660 | 842 | 90 | 290 s |
| exhaustive | 137,026 | 6,897 | 521 | 2766 s |
| GPS radius 200 m | 14,801 | 6,823 | 521 | 286 s |

Whole jobs on house-pc (i3-4330, RX 6750 XT, to the filtered mesh): GPS 200 m 122 min, exhaustive
208 min, the same 521 views and 681 thousand landmarks.

**The gate checks more** (from a cloud task, [PR #5](https://github.com/dspl1236/Cheshire/pull/5)):
- `cpufallback` now also runs feature extraction on the CPU. Before, every GPU switch was off while
  PopSIFT still ran on the card.
- PrepareDenseScene, paired since v0.2.9, is checked by its provenance line and the direct read's
  marker.
- A node that the pairing script declined fails the run at once, with the script's reason, instead
  of hours in.
- The #2344 workaround's warning fails a run: a gate run that needed it should say so.

The HIP build scripts turn GPU SIFT on when a PopSift install is present, and warn when it is not.
Both packagers refuse a package whose feature library does not link PopSift, the v0.3.2 CUDA zip's
failure. `scripts/verify_packages.py` is retired.

## Validation

Each package is gated as the file you download, on its own card. The full gate (the 15-configuration
mini6 matrix, then the 41-view set with `base` and `verify`) runs through Meshroom 2025.1. A shorter
mini6 check (`base`, `defaults`, `cpufallback`, `verify`) runs through Meshroom 2023.3. Each run is scored
at eight nodes: the seven GPU ports and the paired SfM node as before, and PrepareDenseScene, new in
this gate.

| package | hardware | 2025.1: mini6 | 2025.1: 41 views | 2023.3: mini6 |
|---|---|---|---|---|
| Windows AMD | RX 9070 (rocm7.2 gfx12-generic payload) | 15/15 at 8/8 | base 478 s and verify 832 s at 8/8 | 4/4 at 8/8 |
| Windows AMD | RX 5500 XT (hip6.2 gfx1012 payload, bench-pc) | 15/15 at 8/8 | base 1469 s and verify 2377 s at 8/8 | 4/4 at 8/8 |
| Linux AMD | RX 6750 XT (house-pc) | 15/15 at 8/8 | base 916 s and verify 1672 s at 8/8 | 4/4 at 8/8 |
| Windows CUDA | GTX 1080 Ti (bench-pc) | 15/15 at 8/8 | base 1343 s and verify 2273 s at 8/8 | 4/4 at 8/8 |
| Linux CUDA | GTX 1080 Ti (house-pc) | 15/15 at 8/8 | base 966 s and verify 1707 s at 8/8 | 4/4 at 8/8 |

Before the rebuild, the 0.3.5 packages were gated on 2025.1 with the 0.3.6 pairing script and
override. They passed the full gate on the RX 9070, the RX 6750 XT and the GTX 1080 Ti.

## Also

* The mesh gate's median gap to upstream Meshroom 2023.3 is placed. Cheshire's dense stages on
  upstream's own SfM sit as close to upstream as upstream's two runs sit to each other, so the gap is
  the SfM of AliceVision 3.4 against 3.2. A read-only comparison of the two
  ([PR #6](https://github.com/dspl1236/Cheshire/pull/6), `docs/notes/sfm-32-vs-34.md`) ranks the bundle
  adjustment's Huber threshold, 16 px to 4 px, first.
* Bundle adjustment on the device was measured and stopped at its first step. The analytic Jacobian
  arithmetic is 21-34 % of Ceres' Jacobian phase; the rest is Ceres' per-block handling
  (docs/notes/ba-device-plan.md). A bundle-adjustment loop of Cheshire's own is 0.3.7's headline.
