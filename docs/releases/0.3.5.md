# v0.3.5 — Meshing's votes on the device, and gates that measure the result

Meshing's visibility votes now run on the device by default, the last host-bound part of its
passes on four-thread machines. Every GPU port now has an in-process check against its CPU
reference. Two new gates measure the result rather than the outputs: one for SfM and one for the
finished mesh. The rest is smaller: the dense point cloud's SfMData is built on every core, the
Linux bundle's EXR reads inflate with libdeflate, image pairing by GPS radius is opt-in, and so is
CheshireJPG in PrepareDenseScene. Pairing now checks each node's command line against Meshroom's
before it replaces the node.

## What changed

Per-step numbers, boxes and checks are in docs/04.

**Visibility votes on the device (6t; default since step 10).** Meshing's two visibility passes
decide, per camera, which vertices each depth-map pixel votes for, and fold the contributions into
the vertices. The device now does both with the host's own expressions, and folds each vertex's
contributions in pixel order, as the ordered host votes apply them. The host only appends the
camera to each voted vertex's list, from a bitmap, one camera behind. Every result is checked
before it is used: a fold probe on 4096 triples before each pass, range-checked indices, and on any
failure the pass is rerun with host votes. After a device error, the rerun is upstream's CPU pass.
Identical to the ordered host reference on every vertex at 6, 41, 107 and 884 views, on the RX 9070
(Windows), RX 6750 XT (Linux), RX 5500 XT (Windows) and GTX 1080 Ti (Linux CUDA).

| box | the passes, host votes to device votes | Meshing node |
|---|---|---|
| house-pc (i3-4330, RX 6750 XT), 884 views | 158.8 s to 116.9 s | 489.9 s to 450.6 s |
| house-pc, engine bay (107) | 16.6 s to 12.7 s | 124.2 s to 120.9 s |
| RX 9070 box (Ryzen 5 5600X), 884 views | 79.6 s to 66.6 s | 237.8 s to 230.3 s |
| RX 5500 XT (FX-8120), 41 views | 37.6 s to 36.7 s | no change |

`CHESHIRE_GPU_VIS_VOTES=0` gives the bucketed host votes. The first version used hipCUB's radix
sort and bugchecked the RX 9070 box (0x119): rocPRIM resolves its configuration on the host from
the device and in the kernel from the compile target, and a generic target is "unknown" there. The
scan and scatter are written by hand now, and a device error ends the device's part in that pass.

**The depth maps are read ahead on several threads** (step 9, `CHESHIRE_GPU_VIS_READERS`, default
3), in camera order, so the result does not depend on the count. More readers helped house-pc a
little on its faster drive and not on the slower one; the default stays 3.

**The dense point cloud's SfMData on every core (6u).** At the end of Meshing, upstream copied the
input SfMData with its landmarks only to clear them, then built one landmark per vertex on one
thread. At 884 views that was 13.8 s; now 3.3 s. `CHESHIRE_DENSE_SFM_CHECK=1` builds upstream's
version too and compares every landmark bit for bit: identical on all 4,071,638 at 884 views.

**The Linux bundle's EXR reads inflate with libdeflate (6v).** Its OpenEXR is 3.1, which uses zlib;
upgrading it would change the bytes of every EXR Cheshire writes. The direct EXR reader now takes
each chunk's compressed bytes and inflates them itself, on OpenEXR's thread pool, with the same
pixels (428 of 428 files identical on house-pc). The 884-view Meshing on house-pc: 464 s to 440 s.
On only with OpenEXR before 3.2; the Windows packages' 3.4 already uses libdeflate.

**Every GPU port has a check now.** `CHESHIRE_GPU_MATCHER_CHECK=1` answers evenly spaced queries of
every search again with upstream's brute force (mini6: 975 of 975 identical).
`CHESHIRE_GPU_FILTER_CHECK=1` reruns DepthMapFilter's CPU vote pass and compares the modal counts
pixel by pixel (6 of 6 cameras identical). Both are in the gate's `verify` configuration.

**Quality gates.** `scripts/quality_gate.py` runs SfM n times per leg and compares landmarks,
RMSE and poses by Welch's t, with the smallest difference each comparison could have seen, and pose
agreement against the baseline's own run-to-run spread. Today's defaults pass against
upstream-equivalent SfM on 41 views and the engine bay. `scripts/mesh_distance.py` measures two
meshes' exact point-to-surface distance both ways, and `quality_gate.py mesh` gates a candidate
against a baseline's own spread, after aligning the two (cameras, then surfaces) and over the
volume both cover. Against upstream Meshroom 2023.3 on the engine bay (two runs each, Meshroom's
defaults, upstream on a GTX 1080 Ti, Cheshire on the RX 9070): PASS, Cheshire's median p95 1.117 %
of the diagonal against upstream's own run-to-run 1.2225 %. The medians across the pipelines sit
about 30 % above upstream's own, a systematic 0.05 % of the diagonal that is not explained yet
(docs/04). The run also found that Meshing's reconstruction volume flips between two sizes run to
run, in upstream too.

**Pairing checks each node's options first.** Before it replaces a node, `meshroom-pair` compares
the options Meshroom's own binary takes with the package's (both `--help` texts, no GPU). A node
whose Meshroom binary takes an option the package lacks stays Meshroom's, and the script names the
option. This is for Meshroom releases after 2023.3: upstream is replacing StructureFromMotion and
PrepareDenseScene with new nodes (docs/roadmap.md, "Upstream's next pipeline").

**Every `CHESHIRE_*` variable is read one way (6q).** About 127 reads in five styles, some of which
turned a check on with `=0`, now go through one header: unset is the default; `0`, `false`, `off`,
`no` or empty is off; anything else is on; a bad number is the default. docs/04 lists the switches
whose behaviour changed.

**Opt-in:**

- GPS-radius image pairing (6w, `CHESHIRE_GPS_PAIRING_RADIUS=<metres>`): every two views with GPS
  within the radius, for grid surveys where the vocabulary tree pairs distant shots. Views without
  GPS keep the method's pairs. `aliceVision_imageMatching` is paired as the ninth node. Checked on
  41 views; the 444-photo survey it is for has not been rerun.
- CheshireJPG in PrepareDenseScene's read (6r, `CHESHIRE_GPU_JPEG=1`): exact on four cards, no
  faster; the decode is not on the node's critical path.
- The leaf-order knn layout (6s, `CHESHIRE_GPU_KNN_LAYOUT=1`): 1 % faster on the RX 9070, about
  50 % slower in the knn kernel on the RX 6750 XT.
- CheshireEXR ([PR #3](https://github.com/dspl1236/Cheshire/pull/3), merged): per-image load
  timings, Corrupt diagnostics, and decoders kept for the process. Still off by default.

## Validation

Each package is gated as the file you download, through Meshroom 2023.3, on its own card. The gate
is the 15-configuration mini6 matrix and the 41-view monstree set (`base` and `verify`), each scored
at seven ports plus the paired SfM node. Two configurations are new: `defaults` and `hostvotes`.

| package | hardware | mini6 | 41 views |
|---|---|---|---|
| Windows AMD | RX 9070 (rocm7.2 gfx12-generic payload) | 15/15 at 7/7 | base and verify at 7/7 |
| Windows AMD | RX 5500 XT (hip6.2 gfx1012 payload) | 15/15 at 7/7 | base and verify at 7/7 |
| Linux AMD | RX 6750 XT (house-pc) | 15/15 at 7/7 | base and verify at 7/7 |
| Linux CUDA | GTX 1080 Ti (house-pc) | 15/15 at 7/7 (11 in the first run, the other 4 rerun after two harness fixes) | base and verify at 7/7 |
| Windows CUDA | GTX 1080 Ti (bench-pc) | 15/15 at 7/7 | base and verify at 7/7 |

Every self-check the `verify` run asserts passed. On the RX 9070, the 41-view verdicts were:

- the GPU matcher: 13,650 of 13,650 and 39,650 of 39,650 sampled queries identical to upstream's
  brute force;
- the depth-map filter's vote pass: 17 of 17 and 24 of 24 cameras identical;
- the direct JPEG read: 41 of 41 images identical;
- the visibility votes on the GPU: identical in both passes;
- the dense point cloud: identical.

The Linux CUDA `verify` run is the matcher check's first run on CUDA.

**What the gate found.** Four problems, all in the tooling that ships around the binaries or runs
the gate, none in the binaries:

- The pairing option check refused every node on Windows. Meshroom 2023.3's Windows binaries list
  `--help`, while its Linux ones and ours (AliceVision 3.4) do not. The check had never truly run on
  Windows before this gate: in the earlier test Meshroom's own binaries crashed on `--help`, and "no
  options" means "cannot tell, pair anyway". `--help` is now left out of the comparison on both
  platforms. Against Meshroom 2023.3 all nine nodes are compatible (14 to 60 options each), and
  DepthMap without its launcher-dropped option is still refused.
- The Windows CUDA zip did not ship `meshroom-pair-check.ps1`, so it paired unchecked. It does now.
- `hostvotes` required the GPU votes' announce line.
- A harness copied without `check_textured_obj.py` crashed the matrix instead of failing
  `texcheck`.

## Also

* `scripts/compare_depthmaps.py --mode exact` counts decoded pixels that differ, so a difference under
  5e-5 is no longer printed as 0.0000 and passed as bit-identical; `bridge_matrix.py` uses it.
* The end-to-end gate has two new configurations: `hostvotes` (the host votes under their check) and
  `defaults` (Meshroom's defaults with nothing overridden: CPU DSP-SIFT, then every GPU port). No
  earlier configuration ran the CPU DSP-SIFT path most users get.
* Known: the mesh still differs between runs of identical input (geogram's cell numbering), which
  is why the mesh gate compares geometry, not bytes.
