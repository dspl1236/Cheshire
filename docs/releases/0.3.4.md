# v0.3.4 — the CPU work around the kernels, and SfM that can repeat itself

Most of this release is CPU work in nodes whose GPU kernels were already fast: DepthMap and
Texturing were waiting on image loads, bundle adjustment rebuilt its problem and re-ran its inner
projection several times per Jacobian, and Meshing's visibility passes were bound by host work.
Incremental SfM can now be made byte-reproducible, and two GPU codecs are in the tree: CheshireEXR,
merged and off by default, and CheshireJPG, a library no node calls yet.

## What changed

Per-step numbers, boxes and gates are in docs/04, the codecs in docs/19 and docs/20. The 884-photo
False Door on house-pc (i3-4330 with 4 threads, RX 6750 XT, Linux), same photos and preset, v0.3.3
plus the knn pragma against a build with steps 5m-5z (steps 6a-6p came later):

| stage | before | steps 5m-5z |
|---|---|---|
| FeatureExtraction / FeatureMatching | 7.9 / 21.0 min | 9 / 21 min |
| StructureFromMotion | 77.9 min | 32 min |
| PrepareDenseScene | 37.5 min | 40 min |
| DepthMap | 395.0 min | 143 min (19 chunks) |
| DepthMapFilter / Meshing | 16.2 / 12.6 min | 17 / 12 min |
| Texturing | 220.6 min | 250 min |
| whole job | 13 h 11 min | 8 h 46 min |

**DepthMap was loading images, not computing.** There the kernels took about 4.5 s of each 28 s
view; the rest was the CPU getting 73 MB EXRs into the image cache. Now a chunk's cameras follow a
nearest-neighbour tour over their centres (5u, `CHESHIRE_DEPTHMAP_ORDER=0`), a batch decodes only
what the device lacks (5t), EXRs are read straight through OpenEXR (5v, `CHESHIRE_EXR_DIRECT=0`),
and OpenImageIO's lanczos3 downscale after each read is computed directly with the same arithmetic
in the same order: 7.32 s to 0.41 s of CPU per 6000x3376 image, 0 of 20,256,000 values different
(5x, `CHESHIRE_RESIZE_EXACT=0`). All CPU. On the RX 9070 box one 12-view False Door chunk went from
117 image loads and 214 s to 42 loads and 94 s, its 24 files byte-identical to the reference. A
chunk is now 48 views, 19 processes at 884 views instead of 74 (5z); on Meshroom 2023.3 pairing
installs a DepthMap node override for that, same UID, caches valid (`CHESHIRE_DEPTHMAP_BLOCK`).

**The depth-map downscale on the device, HIP builds only (6d).** Full-resolution images go up and a
kernel applies the host's tap tables in the host's order. HIP's `__fmul_rn`/`__fadd_rn` contracted
into FMAs and the device fused the multiply by 255 with the conversion to half, until an empty
`asm volatile` barrier stopped both; now the 884-view chunk's 24 files are byte-identical. On the RX
9070 box the chunk barely moves (116 against 120 s; DepthMap there is GPU-bound): the step is for
four-thread hosts. `CHESHIRE_DEPTHMAP_DEVICE_DOWNSCALE=0` gives the host path CUDA builds use.

**Texturing was loading images too.** On the False Door (RX 9070 box) loads were 443 s of the first
486 s pass: the node reads ahead through `std::async`, so every read queued on OpenEXR's one shared
pool. Read-ahead threads now decode on their own thread (6c): that pass 486 s to 243 s. Reading
ahead on every hardware thread but one (6e) did not speed that box up, now bound by its SATA SSD at
283 MB/s; a lone read-ahead, on a host with RAM for two cache slots, keeps the pool (6o; with 6c
alone house-pc's passes went from 14.7 to 32 minutes). Concurrency only; the OBJ is identical.

**StructureFromMotion: bundle adjustment.** Upstream's projection cost is an autodiff functor around
an inner function that is already analytic, evaluated in passes of four derivative components, so
the inner function ran three to five times per residual block per Jacobian (5m). The default is
now `CHESHIRE_BA_JACOBIANS=analytic`, one evaluation and the chain rule by hand, and **it is not
bit-identical to upstream**: on 41 views 18.7 % of Jacobian values differ, by at most 4.38e-10
relative, residuals identical. It became the default on seven 41-view runs whose landmark counts
and RMSE sat inside upstream's own run-to-run spread; the quality gate is 0.3.5. On 41 views (RX
9070 box) the Jacobian phase goes from 13.0 s to 4.3 s and the node from 66.8 s to 56.8 s;
`=stride` is upstream's functor in one pass, bit-identical. Around the solve (5o-5r) the log-only
residual evaluations are skipped (`CHESHIRE_BA_LOG_COST=1`) and the Ceres Problem lives across
solves while every landmark is active, up to 100 poses (`CHESHIRE_BA_PERSIST=0`; about 4 s of 65 s
on 41 views). The analytic path's projection is one walk of the chain for pinhole with no, K1, K3 or
Brown distortion (`CHESHIRE_BA_FUSED_PROJECTION=0`): the 41-view node 59 s to 50-52 s.

**Reproducible SfM, on request (5n).** Always on: each view's resection and each track's
triangulation draw from their own generator instead of one shared across threads
(`CHESHIRE_SFM_TASK_SEED=0`), Ceres orders parameter blocks by key instead of by address, and the
next-best-views ranking has a total order. `CHESHIRE_SFM_DETERMINISTIC=1` also puts bundle
adjustment on one Ceres thread: two such runs are byte-identical to each other and to a
single-threaded run on 6 and 41 views. It gates SfM changes (`scripts/sfmbench.py`) and is not a
default: the 41-view node takes 112-115 s against 64 s. With the defaults, SfM's output is not
upstream's to the bit: the analytic Jacobians, the fused projection and the persistent Problem's
summation order differ by rounding, and the per-task generators draw different samples.

**PrepareDenseScene.** The undistorted images are ZIP (16 scanlines per block) at zlib level 1
instead of upstream's ZIPS at level 4 (5y, 6f): the same pixels, depth maps from either
byte-identical, cheaper to read, and on mini6 1.4 % larger than level 4 for 4.0 instead of 5.7
thread-seconds of writing (`CHESHIRE_PDS_EXR_COMPRESSION=method[:level]`). In the JPEG read, the
decode was 60 of 556 ms per 12 MP photo; the colour conversion and the alpha pass copied full float
images around the colour processor. The direct read (6n) fills colorconvert's own per-row lines
from the 8-bit pixels and applies the same processor: engine bay 107 of 107 EXRs byte-identical,
the node 28.1 s to 19.1 s on the RX 9070 box. CPU only (`CHESHIRE_READ_DIRECT=0`).

**Meshing.** Visibility votes are applied in parallel by vertex bucket, each in pixel order
(`CHESHIRE_GPU_VIS_BUCKETS=0`): at 833 views the passes 110.5 s to 94.5 s, every vertex identical.
The device now builds the queries too (6k, `CHESHIRE_GPU_VIS_BACKPROJECT=0`) with MultiViewParams'
arithmetic operation by operation, every query identical at 6, 41 and 884 views: at 884 views the
passes 105.5 s to 89.2 s (both on the RX 9070 box); it is aimed at four-thread hosts. It also
found HIP's `__dadd_rn`/`__dmul_rn` fusing despite the `fp contract(off)` pragma, the cause of the
Linux knn distance differences (17,383,299 and 18,404,248 of 87,354,192 with v0.3.3 on the RX 6750
XT; now none, and the gate requires none). On the host (6g-6j, 6l): the max observation angle over
unordered pairs, facet weights once per interior facet (0 of 116,323,696 differ at 884 views),
MeshClean with a parallel pre-screen and its setup by counting (identical to upstream's under
`CHESHIRE_MESHCLEAN_CHECK=1`; at 884 views cleaning 44.3 s to 14.0 s, then the setup about 10 s to
0.86-0.91 s). On house-pc's engine bay Meshing went from 159 s to 126 s with these and 6k.

**CheshireEXR, merged, off by default.** A GPU EXR decoder, bit-identical to OpenEXR. With
`CHESHIRE_DEPTHMAP_GPU_EXR=1` (HIP builds) DepthMap decodes into device memory: on the RX 9070, 101
of 101 files identical and depth maps byte-identical. It inflates one chunk per GPU thread, so on the
ZIP level 1 files PrepareDenseScene now writes it is about 5x slower than the host, and files under
1024 chunks stay there. On ZIPS files (`CHESHIRE_PDS_EXR_COMPRESSION=zips:1`) the DepthMap node,
device path against host: 1.5 % faster on the RX 9070 box and 20 % slower on bench-pc (FX-8120,
RX 5500 XT), each on a 48-view False Door chunk with every map byte-identical, and 8.5 % faster on
house-pc's 107-photo engine bay (i3-4330, RX 6750 XT). It stays an experiment: on the RX 5500 XT the
device decode slows as the card fills, and with its own check on, good files came back corrupt
after the check spilled to host memory; both are being worked on (dspl1236/Cheshire#3).

**CheshireJPG, a library for now.** A baseline JPEG decoder and encoder in HIP compute kernels, not
rocJPEG's VCN engine, whose output is libjpeg-turbo's byte for byte (88 of 89 camera files on the
host check, the damaged one handed back; 201 of 201 cases on the RX 9070). It decodes 124 images/s
at four threads and 148 at twelve there, against libjpeg-turbo's 58 and 116 on the Ryzen 5 5600X.
No node calls it; PrepareDenseScene's read is 0.3.5. Both codecs share `hip/port/cheshiregpu`.

are built from the same source as the gfx1012 one and were not run on hardware this round.

## Also

* The max-flow check judges cut values (6p). A minimum cut need not be unique: the 41-view gate
  found the GPU and Boykov-Kolmogorov labellings 2 of 11,773,764 cells apart, cells
  Boykov-Kolmogorov left undetermined, at equal cut values. The check now evaluates both
  labellings in double and the gate asserts equal values. A check only; the cut is unchanged.
* Opt-in: SfM's outlier and unstable-pose passes limited to what each solve changed (5s,
  `CHESHIRE_SFM_LOCAL_PASSES=1`), exact, but about 40 s over the 884-view run either way (43 s
  restricted); its case is thousands of views. The '605 s' in its first commit is retracted.
* `verify` also asserts the device backprojection, votes, MeshClean and direct-read checks. Step
  6l's comparator is named outside its OpenMP loop, where MSVC rejects a lambda (C3014) and the
  Windows CUDA build failed; same comparator, same results.
* Known: the ROCm 7.2.1 `amdhip64_7.dll` bundled for Windows AMD has not loaded code objects on the
  RX 9070 box since it rebooted with a pending Windows update on 2026-09-22, while the driver's own
  runtime in System32 works. The release zip keeps 7.2.1 under `gpu/rocm7.2`, so where the driver
  provides a runtime, that one loads first; the package passed its gate on the RX 9070 that way.
* Known: above 200 photos Meshroom's ImageMatching pairs by vocabulary tree; on a 444-photo DJI
  grid survey SfM then placed 49 views, and `ImageMatching:method=Exhaustive` placed all 444.
* Known: 6n and 6o have no before-and-after measurement on house-pc yet, and the mesh still differs
  between runs of identical input (geogram's cell numbering).
