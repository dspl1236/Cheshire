# v0.3.7 — Grin, a bundle-adjustment solver of Cheshire's own, and SfM four times faster

Incremental SfM's bundle adjustment no longer goes through Ceres. Grin, Cheshire's own solver, runs
Ceres' algorithm step for step without Ceres (the grin without the cat), with the Jacobians and the
reduced camera system built straight from the scene. It hands the large solves to the GPU with every
sum in the CPU's order, and the GPU gives the same bytes as the CPU on every build and card tested.
Around the solver, the host code that grew with the scene is rebuilt without changing a value. On the
884-photo False Door, StructureFromMotion on the RX 9070 box (a six-core CPU) went from 1140 s to
284 s, and bundle adjustment within it from 675 s to 47 s.

## What changed

The design, every step and its measurements are in `docs/notes/ba-own-solver.md`. The SfM steps
around it are in docs/04.

**Grin** (`CHESHIRE_BA_SOLVER=ceres` for Ceres; it announces itself once per run as
`cheshire: BA solver: Grin, Cheshire's own, for the Schur solves`):
- **Ceres' algorithm, step for step.** Levenberg-Marquardt with Ceres' trust-region rules, Jacobi
  scaling, and the line search for bounded problems. Schur elimination feeds a sparse or dense
  Cholesky factorisation, or dense QR when there is no landmark. It walks the same iterates as Ceres
  to rounding.
- **No Problem per solve.** It is built from the SfM data directly, without a `ceres::Problem` or a
  cost function per observation.
- **Its arithmetic is written out without fused multiply-adds** (`baArith.hpp`), so the CPU and the
  GPU round alike. The Windows build had been fusing them inside Ceres' and Eigen's header code.
- **Solves of 200,000 residual rows or more go to the GPU** (`CHESHIRE_BA_DEVICE=0` for the CPU
  alone, `CHESHIRE_BA_DEVICE_MIN_ROWS` for another threshold). The GPU does the evaluation, the
  passes over the Jacobian, the landmark elimination and the back-substitution. The minimiser's
  vectors stay on the device too. The reduced camera system's factorisation stays on the CPU.
- **The GPU gives the CPU's bytes.** Every sum follows the CPU's order, so the output is identical
  either way. `CHESHIRE_BA_DEVICE=check` solves every such problem both ways and compares.

**The same bytes on every build and card.** Each package's binaries, on 41 views and the 107-photo
engine bay, six ways: the CPU twice, the GPU, the GPU against the CPU per solve, the direct build
against the Problem build per solve, and the defaults.

| build | card | GPU against CPU, per solve | output |
|---|---|---|---|
| Windows AMD (ROCm 7.2, gfx12) | RX 9070 | 29/29 and 35/35 the same | one digest per set |
| Windows AMD (HIP 6.2, gfx1012) | RX 5500 XT | 29/29 and 34/34 the same | one digest per set |
| Windows CUDA | GTX 1080 Ti | 29/29 and 34/34 the same | one digest per set |
| Linux CUDA | GTX 1080 Ti | 29/29 and 36/36 the same | one digest per set |
| Linux AMD | RX 6750 XT | 29/29 and 36/36 the same | the Linux CUDA build's digests |

The two Linux packages give the same bytes on an NVIDIA card and an AMD card. The builds do differ
from each other: the Windows AMD families are compiled for AVX and AVX2, and Linux uses glibc's
maths, so the host code rounds differently between them.

**SfM around the solver** (steps 7g-7m, all exact: the output is unchanged):
- **7g:** incrementalSfM's OpenMP threads sleep at once after a parallel region (Windows). LLVM's
  runtime otherwise spins them for 200 ms beside the single-threaded passes that follow, about 5 % of
  the run. `CHESHIRE_OMP_BLOCKTIME=<ms>` sets another time.
- **7h:** `CHESHIRE_SFM_PROFILE=1` prints where the reconstruction's time goes.
- **7i:** colours are assigned to views in one pass (47 s to 37 s on the False Door).
- **7j:** a track-id mask replaces a 1.35-million-node set that was rebuilt in the next-views scoring,
  every view's resection and the local-BA graph. Resection went from 79 s to 42 s and the next-views
  scoring from 29 s to 8 s.
- **7k:** triangulation runs without its critical sections.
- **7l:** upstream's outlier and unstable-pose passes after each solve run on every core (54 s to
  15 s).
- **7m:** the local-BA graph's states run on every core.

| False Door, RX 9070 box | 0.3.6 (Ceres) | 0.3.7 |
|---|---|---|
| StructureFromMotion | 1140 s | 284 s |
| of which bundle adjustment | 675 s | 47 s |

The two were measured on different days on the same box, where the same build's times drift by 20 %
or more between days. The steps between them were measured back to back. The largest pieces left are reading the features
(46 s), the colours' image reads, and the arithmetic of resection and triangulation.

**Output compared with 0.3.6.** The solver does not reproduce Ceres to the bit: its sums run in an
order of its own, and it rounds without fused multiply-adds. Its trajectories stay within Ceres' own
run-to-run spread: the SfM quality gate passed on 41 views, the engine bay and the False Door when Grin
became the default (docs/notes/ba-own-solver.md, step 3).

**SfM repeats itself by default now.** The solver's sums do not depend on the thread count, so on
every build every repeated run gave the same bytes: every False Door run on the RX 9070, and the
repeated CPU runs of the exactness checks. Up to 0.3.6 that took `CHESHIRE_SFM_DETERMINISTIC=1`,
which ran Ceres on one thread.

**Packaging.** `aliceVision_sfm_bundle.dll` carries GPU code now, so the Windows AMD package ships it
per GPU target, the seventh such DLL. Without that, every target but the two base packages' would have
had no copy at all.

15-configuration mini6 matrix and 41 views (`base`, `verify`) through Meshroom 2025.1, and a shorter
mini6 check (`base`, `defaults`, `cpufallback`, `verify`) through 2023.3. Every run is scored at eight
nodes. The SfM node now also has to announce Grin.

## Also

* **What repeatable SfM showed.** The gate's 41-view `base` and `verify` runs now give the same bytes
  on all three AMD cards, the RX 9070, the RX 6750 XT and the RX 5500 XT. Up to 0.3.6, SfM made every
  run different. On the CUDA packages the two runs still differ, and the difference starts at
  feature extraction:
  - the keypoints are identical;
  - out of about 970,000 descriptors, one (Windows) or four (Linux) come out differently on the
    GTX 1080 Ti;
  - the one examined closely has the same bins at different magnitudes, which points at a race in
    PopSIFT's CUDA descriptor kernel. The HIP build of PopSIFT repeats exactly.

  Every run still passed the gate. Finding the race is the next step.
