# v0.4.0 — upstream's new SfM pipeline, paired: Photogrammetry Experimental on Meshroom 2025.1 in less than half the time

Meshroom 2025.1 ships upstream's next structure-from-motion pipeline as **Photogrammetry Experimental**.
TracksBuilding, RelativePoseEstimating, SfMBootStrapping and SfMExpanding replace StructureFromMotion, and
IntrinsicsTransforming and ExportImages replace PrepareDenseScene. An AliceVision maintainer has said the old
nodes will be replaced in the next release ([AliceVision discussion
2116](https://github.com/alicevision/AliceVision/discussions/2116)). Until now that pipeline ran on Meshroom's
own binaries even with Cheshire paired. From v0.4.0 the pairing covers its eight programs too, seventeen nodes
on Meshroom 2025.1, and Cheshire's SfM work is ported to them. On 41 photos the Experimental graph's nodes take
357 s instead of 743 s with those eight on Meshroom's own binaries, and SfMExpanding takes 29 s instead of 334
s. A Fast Ransac copy of the template joins the other two. Meshroom 2023.3 pairs as before, nine nodes, since it
has no such pipeline.

## What changed

The measurements are in docs/04 (the sections "After 0.3.9") and docs/15 (NACRANSAC).

**The new pipeline, paired** (Meshroom 2025.1). Both pairing scripts pair TracksBuilding,
RelativePoseEstimating, SfMBootStrapping, SfMExpanding, SfMTransform, SfMColorizing, IntrinsicsTransforming and
ExportImages.
- **Only where Meshroom ships the pipeline**, its own `aliceVision_sfmExpanding` being the sign. Meshroom 2023.3
  carries three of the eight binaries and no template that runs them, and is left alone.
- **Each goes through the option check**, as the other nodes do. The check now also refuses a binary that
  *requires* an option Meshroom's own does not know.
- **Step 9l:** upstream's SfMBootStrapping gained a required `--method` after the AliceVision that 2025.1 ships,
  and 2025.1's node never passes it. Ours infers it as 2025.1's own binary bootstraps: from the mesh when
  `--meshFilename` names one, otherwise from the pairs.
- **Meshroom's Photogrammetry is unchanged**: it is still the legacy pipeline, StructureFromMotion and all, and
  still paired. Photogrammetry Experimental is the template that now runs on Cheshire.

**Cheshire's SfM work on the new nodes** (steps 9a-9k). Most of the legacy pipeline's SfM work reached only the
legacy nodes; Grin's bundle adjustment and the colours' 8-bit read carried over by themselves. These steps port
the rest. Each gives upstream's results to the bit except 9c, whose draws differ (9d's EXR files are compressed
differently, with the same pixels, and 9j is opt-in):
- **9a, NACRANSAC skips the models that cannot win.** The new nodes' AC-RANSAC takes 0.3.8's bound and key sort.
  SfMExpanding went from 236.5 s to 60.0 s on 41 views, and from 108.0 s to 43.3 s on the 107-photo engine bay.
  On one thread its files are byte for byte upstream's path's.
- **9b, one resection on every core.** Most of SfMExpanding's rounds resect a single view, so NACRANSAC's 50,000
  iterations ran on one thread. They now run in speculative batches on every core, with the loop's answer: 55.6
  s to 28.3-29.5 s on 41 views. `CHESHIRE_ACR_BATCH_CHECK=1` runs the loop as well and compares.
- **9c, SfMExpanding repeats itself.** Upstream's triangulation draws every track's samples from one generator
  shared across threads, so no two runs of SfMExpanding were the same. Each track now draws from its own
  generator, as the legacy SfM's tasks have since 0.3.4. Two runs give the same bytes, at 12, 4 or 1 threads.
  The draws differ from upstream's: camera centres stay within 0.0060 % (41 views) and 0.12 % (engine bay) of
  the scene's radius of a stock run's, where a run with upstream's shared generator lands 0.0094 % and 0.21 %
  from it. `CHESHIRE_SFM_TASK_SEED=0` restores the shared generator.
- **9d, 9g and 9i, ExportImages as PrepareDenseScene.** One image per thread, the EXR at ZIP level 1 with
  libdeflate, the warp's map built once per camera, and on hosts of four threads or fewer the warp on the GPU,
  to the bit: 28.3 s to 9.3-9.9 s on 41 views and 57.0 s to 18.1-19.3 s on the engine bay, with the same pixels.
- **9e and 9h, the tracks file.** Every new node after TracksBuilding parses its JSON tracks file again. It is
  now parsed straight into structs, without copying the DOM, with Boost.JSON's own numbers:
  RelativePoseEstimating on the engine bay 31.2 s to 18.8 s.
- **9j, the 5-point solver's nullspace by QR,** opt-in as the 7-point solver's is (`CHESHIRE_QR_NULLSPACE5=1`):
  about 5 % of RelativePoseEstimating, for results that agree to rounding and RANSAC's spread, not to the bit.
- **9k:** the tracks parse announces which way the file went, so the gate can see it.

On the nightly's inputs, replaying each node's command line on the RX 9070 box, the new chain from
TracksBuilding to ExportImages:

| | upstream's binaries | 0.3.8's build | v0.4.0 |
|---|---|---|---|
| 41 views | 397.9 s | 285.0 s | 53.0-56.4 s |
| engine bay, 107 photos | 291.2 s | 201.7 s | 78.0-83.0 s |

Our legacy chain, StructureFromMotion and PrepareDenseScene, took 77.5 s and 55.4 s on the same sets with
0.3.8's build.

**Photogrammetry Experimental Fast Ransac.** Pairing on Meshroom 2025.1 now writes a third template: the
Experimental graph with 2023.3's RANSAC counts, FeatureMatching's 2048 and SfMExpanding's 4096. On 41 photos its
nodes took 339 s against the template's 357 s with Cheshire paired, and 457 s against 743 s with the new
pipeline's nodes on Meshroom's own binaries, with all views placed. The generators also take a Photogrammetry
whose SfM node is SfMExpanding, as upstream's nightly ships it, so the next Meshroom gets its Fast Ransac copies
too.

**Pairing fixes:**
- **A node a run leaves to Meshroom gets Meshroom's binary back.** It kept an earlier pairing's launcher, so
  re-pairing with an older package left the new pipeline's nodes on the newer one while the script said
  "Meshroom keeps its own binary".
- **`pair` refuses a node Meshroom does not have**, where it planted a launcher with nothing behind it.
- **The Fast Ransac generators**, after two adversarial review rounds: a user's file named like ours is
  recognised by its whole numbers (a user's 20480 counted as ours, and was overwritten); `meshroom-pair.cmd`
  makes both folders absolute, so a trailing backslash no longer runs the install on `--unpair`; an unparseable
  template no longer stops the script before the next one is written, a non-UTF-8 file under our name no longer
  crashes the Linux script, and both systems treat a malformed template alike.
  `scripts/check_fast_ransac_templates.py` checks both generators against 29 crafted inputs.

## Validation

Each package is gated as the file you download, on its own card. The gate is 0.3.8's with the new pipeline
added: the mini6 matrix and 41 views through Meshroom 2025.1, and a shorter mini6 check through 2023.3. New in
0.4.0:
- `experimental` and `fastransacexp` run Photogrammetry Experimental and its Fast Ransac copy by name, and score
  fourteen nodes: the six GPU nodes and the new pipeline's eight, each held to the launcher's provenance line
  and to what our build of it announces;
- `verifyexp` runs the new pipeline under its self-checks: NACRANSAC's bound and batches against the loop, the
  tracks file's parse against Boost.JSON's DOM, the colours' read, and in ExportImages the direct read, the
  libdeflate writer and the GPU warp, the last two switched on whatever the platform's default;
- a failing count or a fallback in any of those nodes fails every configuration.

| package | hardware | 2025.1: mini6 | 2025.1: 41 views | 2023.3: mini6 |
|---|---|---|---|---|
| Windows AMD | RX 9070 (rocm7.2 gfx12-generic payload) | 19/19 | base 388 s, verify 821 s, experimental 359 s, fastransacexp 343 s, verifyexp 858 s | 4/4 |
| Windows AMD | RX 6750 XT (hip6.2 gfx1031 payload, bench-pc) | 19/19 | base 783 s, verify 2069 s, experimental 769 s, verifyexp 2213 s | 4/4 |
| Linux AMD | RX 5500 XT (house-pc) | 19/19 | base 886 s, verify 1932 s, experimental 896 s, verifyexp 2063 s | 4/4 |
| Windows CUDA | not run on an NVIDIA card in this release (below) | | | |
| Linux CUDA | GTX 1080 Ti (house-pc) | 19/19 | base 666 s, verify 1727 s, experimental 681 s, verifyexp 1842 s | 4/4 |

109 runs on four cards, none failed. Every legacy run scored eight of eight nodes and every run of the new
pipeline fourteen of fourteen. Every self-check came out identical on every card, the new ones included: on 41
views the batch check found 28 of 28 calls returning the loop's answer, the tracks file's four loads 0 tracks
different, and the device warp each image identical.

On the Windows cards and the GTX every configuration that ran before gave the depth maps of the last gate on the
same card (0.3.8's or 0.3.9's) byte for byte, except `blast`, which now also turns on the opt-in 5-point QR, and
`cpufallback`, whose digest has changed with every release since 0.3.6 while `base`'s held. The new pipeline
repeats itself as well: `experimental` and `verifyexp` gave the same depth maps on each card.

**The Windows CUDA zip was not run on an NVIDIA card in this release.** Its test box lost its boot drive after
the GTX 1080 Ti went in, before the gate began. It ships on its build checks: GPU SIFT linked, the CUDA, MSVC
and OpenMP runtimes bundled, all eight new-pipeline programs present, built by the same chain from the same
sources as the gated packages. On the RX 9070 box, with no NVIDIA card, its eight new-pipeline programs also ran
the 41-view Photogrammetry Experimental command lines of this gate from the zip alone: all finished, and
SfMExpanding placed all 41 cameras within 0.0028 % of the scene's radius of the AMD zip's reconstruction. If you
run it, a note on how it went is welcome.

House-pc's RX 5500 XT was reset by its driver nine minutes into the gate (an sdma0 ring timeout, then "VRAM is
lost due to GPU reset!"), and the card carried on. Every run before the reset gave 0.3.9's depth maps; after it,
five runs gave maps about 1 % of the pixels apart, a relative 3e-6 at the median, and 0.3.8's bundle did the
same on the same inputs. After a reboot both bundles gave 0.3.9's maps six times out of six. The details are in
docs/04.

## Also

* **Upstream:** the shared generator in SfMExpanding's triangulation, which 9c replaces, is reported as
  [alicevision/AliceVision#2193](https://github.com/alicevision/AliceVision/issues/2193), measured on upstream's
  own nightly binary.
* **Known:** neither Windows zip can write a USD file (a node told to write `.usda` stops with 0x80000003): they
  ship USD's libraries without its plugin resources. No node of Meshroom 2025.1's or 2023.3's templates reads or
  writes one; the fix comes with the pivot (docs/04, roadmap).
* **Next:** the pivot proper, when a Meshroom release makes the new pipeline its Photogrammetry: the AliceVision
  submodule moved to that release, USD, and the legacy SfM's persistent problem and ranking ties ported to the
  new nodes (docs/roadmap.md).
