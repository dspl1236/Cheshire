# v0.4.4 — FeatureMatching in half the time on large sets, and GPU SIFT ready for RDNA chips that are not out yet

On large sets most of FeatureMatching's time was the geometric filter on the CPU, while the GPU waited. Three exact
steps change that. The filter's 7-point fits run four at a time in AVX2 lanes, each view's descriptors stay on the GPU
for all of its searches, and the GPU searches the next image pair while the CPU filters this one. On the 884-photo
False Door (an RX 9070), FeatureMatching takes 42.7 and 43.3 s against 0.4.3's 85.0 and 76.5 s. Those are both release
packages, run alternately on an idle box, and the match file is byte for byte 0.4.3's.

The AMD packages also stop naming each chip. The Linux bundle and the Windows zip's ROCm 7.2 payloads carry one generic
code object per RDNA family, GPU SIFT included. A card of those families that ships after this release runs on the GPU
without a new build. GPU SIFT from a generic code object had crashed since v0.2.17; the cause is found and fixed (15b).

## What changed

The measurements are in docs/04 (the sections "After 0.4.3", "0.4.4 packaging I" and "The 0.4.4 release round"). The
per-step times below are the development build's on the False Door.

**13a, the 7-point fits four at a time.** AC-RANSAC's fit spends three quarters of its time in Eigen's SVD of a 9x9
matrix. It now runs four samples at once in AVX2 lanes, each lane the same IEEE operations as Eigen's code (with fused
multiply-adds exactly where the compiler fuses Eigen's statements, checked at startup). All 43.6 million fits of the
False Door were compared with Eigen's: identical. `CHESHIRE_ACR_SVD_LANES=0`. FeatureMatching 85 s to 71 s.

**14a, each view's descriptors uploaded once.** The GPU matcher uploaded a view's descriptors for every pair it was
in. They now stay on the GPU for the node's run, within a memory budget. `CHESHIRE_GPU_MATCHER_RESIDENT=0`. 71 s to
62.5 s.

**14b, the next pair's search queued during this pair's filter.** `CHESHIRE_GPU_MATCHER_AHEAD=0`. 62.5 s to 47 s.

13a is CPU code and 14a and 14b are the GPU matcher's, so all three are in the CUDA packages too.

**Generic code objects on Linux.** The Linux AMD bundle named 19 chips. It now carries Vega (gfx900, gfx906), RDNA1 by
name (gfx1010-1012) and one generic code object each for RDNA2, RDNA3 and RDNA4 (`gfx10-3-generic`, `gfx11-generic`,
`gfx12-generic`). The RDNA2 APUs are covered with the rest.

**15b, GPU SIFT from a generic code object.** Since v0.2.17 a PopSIFT built for a generic target crashed on the first
photograph (exit 0xC0000094), so GPU SIFT was built for each chip by name. The cause was PopSIFT's grid filter. Its GPU
steps are rocThrust, whose kernels compile to nothing under a generic target, and the empty counts led to a divide by
zero. The filter now runs on the CPU, with byte-identical features, and PopSIFT is built for the same generic targets
as the rest (the Linux library 170 MB to 58 MB). `CHESHIRE_POPSIFT_HOST_FILTER=0`. AMD packages only.

**15a, CPU SIFT where GPU SIFT has no code for the card.** A card that PopSIFT has no code object for used to fail
inside PopSIFT, where nothing could catch it. FeatureExtraction now checks the loaded PopSIFT library for the card's
code object, or its family's generic one, and takes CPU SIFT with a warning when neither is there. AMD packages only.

**Measured and dropped:** giving FeatureMatching's search thread more of the CPU (M3). With 14b the GPU search and the
CPU filter each sit at their own floor.

**Caught before release.** The Windows gate found two log lines that did not say what ran: under the matcher profile
(`CHESHIRE_GPU_MATCHER_LOG=1`) 14b searched one pair at a time without saying so, and with the QR nullspace on, 13a's
report announced AVX2 lanes that had not run. Both log what runs now. The packages were rebuilt and every gate run
again; the first build was not published.

## Validation

Each package was checked as the file you download, on its own card where one was available (docs/04, "The 0.4.4
release round").

| package | hardware | 2025.1: mini6 | 2025.1: 41 views | 2023.3: mini6 |
|---|---|---|---|---|
| Windows AMD | RX 9070 (rocm7.2 gfx12-generic payload) | 19/19 | base 297 s, verify 691 s, experimental 272 s, fastransacexp 257 s, verifyexp 696 s | 4/4 |
| Linux AMD | RX 6750 XT (house-pc, GPU SIFT from `gfx10-3-generic`) | 7/7 | experimental 511 s, and 566 s with 13a-15b off: the same depth maps | 1/1 |
| Linux CUDA | GTX 1080 Ti (house-pc) | 7/7 | experimental 571 s (0.4.3: 636 s) | 1/1 |
| Windows CUDA | not run on an NVIDIA card in this release (below) | | | |

Every run passed, and every depth map is the previous gate's on the same card byte for byte, except the RX 9070's two
`cpufallback` runs: CPU SIFT's features differ from run to run (below). On the RX 6750 XT under Linux, the 41 views
take 9.7 % less than with this release's steps off, which is 0.4.3's time, and on the GTX 1080 Ti 10 % less than in
0.4.3's gate.

**The Windows CUDA zip was not run on an NVIDIA card in this release**, nor in 0.4.0 to 0.4.3: its test box is still
down. Its eight new-pipeline programs ran this gate's 41-view Photogrammetry Experimental command lines on the RX 9070
box from the zip alone; all finished, and SfMExpanding placed all 41 cameras within 0.0028 % of the scene's radius of
the AMD zip's reconstruction. If you run it on a card, a note on how it went is welcome. The Windows AMD zip's hip6.2
payloads (RDNA1, and RDNA2 under Windows) were not run on a card either. Their code is the gated payloads' code,
compiled for their targets by the same chain, and their PopSIFT is still built per chip.

## Also

* **Known:** CPU SIFT (`--forceCpuExtraction`, or 15a's fallback) is upstream's, and its features differ from run to
  run: its threads add keypoints in the order they finish. GPU SIFT repeats exactly.
* **Known:** neither Windows zip can write a USD file, as in 0.4.0.
* **Upstream:** [alicevision/AliceVision#2194](https://github.com/alicevision/AliceVision/pull/2194) (a draft
  functional test for SfM) and [alicevision/AliceVision#2193](https://github.com/alicevision/AliceVision/issues/2193)
  (the SfMExpanding race) are open.
