# v0.4.3 — DepthMap's image uploads without stopping the GPU: the same depth maps, the False Door's DepthMap 9.6 % shorter

On AMD cards, DepthMap's image uploads stopped the whole GPU. Upstream's upload path frees and reallocates each cache
slot, creates and destroys a texture per mipmap level, and synchronises the device twice. On HIP a free and a
texture's teardown also wait for every queued kernel, so every upload left the device idle. Three exact steps take
those waits out and move the uploads under the GPU's work. On the 884-photo False Door (Photogrammetry Experimental
Fast Ransac, Meshroom 2025.1, an RX 9070), the DepthMap node's chunks take 1,142 s against 0.4.2's 1,263 s (both release
packages, run alternately chunk by chunk on an idle box). All 1,652 of its depth and similarity maps are the same
bytes as 0.4.2's.

## What changed

The measurements are in docs/04 (the sections "After 0.4.2").

**12a, the uploads on a stream of their own.** A depth map cache slot keeps its mipmapped array and its textures once
it has them. A new image of the same size is refilled in place, on a stream of its own: the same downscale, colour
conversion and level builds as before, into the kept array, with nothing freed and no device-wide wait. A False Door
chunk 54.9 s to 53.5 s.

**12b, the next batch's images uploaded during this batch's tiles.** After each tile is queued, one of the next batch's
images (already decoded on the CPU since 0.4.1) is uploaded into a cache slot that no camera of this batch or the next
uses. The next batch finds them on the GPU: on a False Door chunk 58 images move under the tiles, and the later
batches' loads drop from 1.2 s to 0.1 s. A chunk 53.5 s to 52.2 s.

**12c, a batch's uploads while its images decode.** A batch's load now uploads each image as soon as it is decoded,
while the rest of its group decodes, each file on its own thread. Images that are already decoded go up first. The
first batch's load 2.30 s to 1.93 s.

Each step has a switch that restores upstream's behaviour: `CHESHIRE_DEPTHMAP_UPLOAD_STREAM=0` (which also turns off
12b), `CHESHIRE_DEPTHMAP_PREFETCH=0`, `CHESHIRE_DEPTHMAP_LOAD_PIPELINE=0`. The steps are HIP only: CUDA's frees do not
wait on the device, and the CUDA packages keep upstream's uploads and say so in the log.

**Caught before release.** 12c as first written had a race. An image that was already decoded could be overwritten by
another image's decode while it was being copied to the GPU, because the image cache reuses a buffer in place. It hit
about one view in 800: on the False Door, one depth map per run had a band of another camera's rows. Replays of single
chunks never showed it; the release round's whole-node comparison against 0.4.2 did. The fix uploads those images
before any decode starts. The packages were then rebuilt and every gate run again, and the comparison now matches 0.4.2
on all 1,652 maps, in three runs of the fixed code and two of the rebuilt package. The first build was not published.

**Measured and dropped:** Meshing's visibility passes are latency-bound, not FP64-bound (an exact float-filtered walk
was no faster), and FeatureMatching's transfers are already hidden behind its geometric filter (docs/roadmap.md).

## Validation

Each package was checked as the file you download, on its own card where one was available (docs/04, "The 0.4.3
release round").

| package | hardware | 2025.1: mini6 | 2025.1: 41 views | 2023.3: mini6 |
|---|---|---|---|---|
| Windows AMD | RX 9070 (rocm7.2 gfx12-generic payload) | 19/19 | base 312 s, verify 685 s, experimental 277 s, fastransacexp 252 s, verifyexp 696 s | 4/4 |
| Linux AMD | RX 6750 XT (house-pc) | 7/7 | experimental 566 s, and 566 s with 12a-12c off: the same depth maps | 1/1 |
| Linux CUDA | GTX 1080 Ti (house-pc) | 7/7 | experimental 636 s | 1/1 |
| Windows CUDA | not run on an NVIDIA card in this release (below) | | | |

Every run passed, and every depth map is the previous gate's on the same card byte for byte, except the RX 9070's
`cpufallback`, whose digest changes from run to run. On the RX 9070 the 41-view runs take 0.3-7 % less than in 0.4.2's
gate. On the RX 6750 XT under Linux, 12a-12c made no measurable difference to the 41 views. They stay on there: they
are exact and cost nothing on that card.

**The Windows CUDA zip was not run on an NVIDIA card in this release**, nor in 0.4.0 to 0.4.2: its test box is still
down. Its eight new-pipeline programs ran this gate's 41-view Photogrammetry Experimental command lines on the RX 9070
box from the zip alone; all finished, and SfMExpanding placed all 41 cameras within 0.0028 % of the scene's radius of
the AMD zip's reconstruction. If you run it on a card, a note on how it went is welcome. The Windows AMD zip's hip6.2
payloads (RDNA1, and RDNA2 under Windows) were not run on a card either; their code is the gated payloads' code,
compiled for their targets by the same chain.
